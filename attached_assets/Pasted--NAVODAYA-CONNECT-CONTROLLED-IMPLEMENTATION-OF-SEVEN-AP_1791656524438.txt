Act as a senior full-stack software engineer working on my existing Navodaya Connect application.

These restrictions take priority over implementation preferences.

1. Memories social-post system.

Do not redesign, replace, remove, rename, or refactor unrelated parts of the application.

Preserve the existing:

* Authentication, sign-in, registration, and onboarding flows.
* Firebase configuration and working authentication.
* PostgreSQL/Neon database and Drizzle ORM architecture.
* API-server architecture and existing API contracts.
* Four role definitions and existing role-specific permissions.
* Existing profile fields, account records, and user data.
* Branding, colors, typography, icons, and visual identity.

* Existing working features, navigation destinations, and business logic.

Do not introduce new features beyond the seven approved change groups.

Do not perform general modernization, broad refactoring, unnecessary dependency upgrades, or unrelated security work.

Do not delete working functionality simply because implementing an alternative is easier.

### 2.3 Smallest-change principle

Before modifying a file, establish why the change is necessary.

Reuse existing components, APIs, database models, services, and UI patterns wherever possible. Prefer small, targeted, backward-compatible changes.

You may modify shared components or backend files when a direct dependency requires it, but their unrelated behavior must remain unchanged.

Do not expose, print, replace, or overwrite secrets. Do not commit local environment files or credentials.
